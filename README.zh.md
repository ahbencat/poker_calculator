# 德州扑克在线胜率计算器

**[在线体验](https://ahbencat.github.io/poker_calculator/)** ·
简体中文 | [English](README.md)

**德州扑克（Texas Hold'em / NLHE）胜率计算器，即 poker odds calculator**：为 2–10 位
玩家选择手牌与公牌，实时计算每位玩家的 胜 / 平 / 负 概率。胜率全部来自**精确枚举**
（含翻牌前，无抽样误差）——蒙特卡洛搜索虽已实现但在页面上已停用；纯**原生 JavaScript**
在浏览器本地完成全部计算——零依赖、无构建、可离线（双击 `index.html` 即用）。
界面支持中/英文切换（顶栏按钮）。

> - 核心概率计算算法（模式选择、7 张牌评估器、精确枚举、蒙特卡洛）的详细实现与流程图
>   见 [docs/algorithm.md](docs/algorithm.md)
> - 依赖事实清单与工具链要求见 [docs/dependencies.md](docs/dependencies.md)

## 功能

- **玩家增减**：任意增删玩家（最少 2 位，最多 10 位）；增删未参与的玩家、
  给新玩家选第 1 张牌等**不改变计算输入的操作不触发重算**、不打断进行中的计算
- **计算门槛**：至少 2 位玩家各 2 张手牌后才开始计算（不论桌人数），
  只计算手牌齐全的玩家，未齐玩家完全不参与
- **精确手牌**：52 张牌选择器，已选的牌全局自动置灰
- **公牌可选**：翻牌 / 转牌 / 河牌任意阶段，未发的牌自动补齐
- **页面恒用精确枚举**（全自动，无感知切换）：
  - 参与玩家手牌齐全 → **精确枚举**（含翻牌前，结果精确无误差）
  - 翻牌前等重枚举 → 先出 100ms 蒙特卡洛预览，完成后无缝替换为精确值
  - **蒙特卡洛搜索已实现但已停用**——引擎的 MC 主路径与全随机分支作为
    测试覆盖的 API 保留；页面交互（只齐牌参与）恒判为精确枚举
- **界面双语**：顶栏一键中/英切换，选择会被记住
- **牌桌界面**：真实扑克牌版式（左上点数 / 右下花色的竖版白卡面）、
  绿毛毡桌面 + 木质围栏公牌区；手机竖屏优先（单列布局、底部弹层选牌、
  触控目标 ≥ 44px）

## 运行

```bash
# 方式一：静态托管（推荐，手机可通过局域网访问）
python3 server.py            # 默认 0.0.0.0:8000，打印局域网地址
python3 server.py 9000       # 指定端口
python3 server.py 8000 127.0.0.1   # 仅本机可访问

# 方式二：直接双击 index.html（file:// 协议同样可用）
```

无任何构建步骤与第三方依赖（服务器为 Python 3.7+ 标准库）。

## 技术要点

- **评估器**：4 个"恰好出现 k 次"rank 掩码无分支状态机 + 花色 4 字节车道计数
  （无同花时零掩码构建），3 张 8192 项小表（顺子/popcount/top5），单次评估零分配；
  判定顺序利用"7 张内同花不与四条/葫芦共存"
- **精确枚举**：里程计式组合枚举（最末轮快路径），状态可暂停恢复；
  每 2048 局面检查一次时限
- **蒙特卡洛**（已实现，主模式已停用）：部分偏置 Fisher–Yates、mulberry32 可种子化、
  样本方差置信区间、时间预算 650ms / SE<0.15% 提前停；保留为测试覆盖的引擎 API，
  页面上仅用于 100ms 快速预览
- **重算抑制**：输入签名（齐牌玩家手牌 + 公牌）判定，签名不变的操作零重算；
  行 DOM 重建时回放最近结果
- **UI 不卡顿**：计算以 12ms 分片经 MessageChannel 让出主线程（避开 setTimeout 4ms 钳制）；
  翻牌前重枚举期间持续显示预览值，精确值就绪后无缝替换
- **file:// 兼容**：刻意不使用 ES Modules、Worker 与任何第三方依赖
  （file:// 下被浏览器同源策略拦截）

## 蒙特卡洛：搜索逻辑与停用逻辑

### 搜索逻辑（引擎 `createMcTask`）

MC 任务运行时，每次迭代抽样一副随机牌局：

1. **随机数** — `mulberry32`，可通过 `opts.seed` 播种（测试固定种子保证确定性）；
   默认种子混合 `Date.now()` 与 `Math.random()`。
2. **部分 Fisher–Yates 洗牌** — 只洗可用牌堆的前
   `need = 未知手牌数 + 未知公牌数` 个位置（已知牌与死牌已提前剔除），
   即从剩余多重集中均匀抽走恰好缺失的那些牌；先填未知手牌槽，再填未知公牌槽。
3. **结算本局** — 评估全部 P 位玩家的 7 张牌，找出最高分与赢家数 `w`；
   每位赢家累计 `1/w` 权益（除法走查表），同时累加 `win`/`tie` 计数；
   `eq²` 同步累计以算样本方差。
4. **停止规则** — `maxIters` 每次迭代都检查，其余每 1024 次迭代检查：
   - 下限 `minIters` = 10,000 次；
   - 上限 `maxIters` = 400,000 次；
   - 时间预算 `budgetMs` = 650ms；
   - 精度：全体玩家最大标准误 < 0.15%（由 `eq` 的样本方差推算）。
5. **输出** — 每玩家 `equity / win / tie / se`；徽标显示
   `蒙特卡洛 · N 次模拟 · ±X%`。

两个特例：

- **全随机局面**（未指定任何手牌）：玩家间可交换，胜率*精确*等于 `1/P`——
  这是数学事实而非估计——以 `uniform: true` 返回；win/tie 在玩家间取平均以降噪，
  任务达到 `minIters` 即停。
- **100ms 预览** — 页面实际会跑的唯一 MC 路径：精确枚举较重时（评估 ≥ 50 万次，
  如翻牌前）先以 `budgetMs: 100, minIters: 5000, maxIters: 60000`（SE 目标关闭——
  只按迭代上限与时间截断）跑同一套例程，随后交给精确枚举；预览在被精确值替换前
  持续可见（`provisional` 标记 → “快速预估”）。

### 停用逻辑（页面为何不以 MC 为主计算模式）

模式判定在 `Engine.createTask` / `classify`：

```
mode = unknownHoles === 0 && exactEvals <= 6,000,000 ? "exact" : "mc"
```

页面要进入 `"mc"` 分支必须推开两扇门之一——而这两扇门都被刻意封死：

1. **不可能缺手牌**：UI 计算门槛（app.js 的 `completeIndexes()`）只让已选满
   *两张*手牌的玩家参与，故 `unknownHoles` 恒为 0。
2. **不可能超出精确预算**：页面可达的最重输入是 4 人翻牌前——
   `C(44,5) × 4 = 4,344,032` 次评估，为 2–10 人 × 全部街道的极大值——
   稳稳低于 6,000,000 次保险丝（`EXACT_BUDGET`）。

因此每次页面交互 `classify` 都返回 `"exact"`：MC **主路径**与全随机分支从 UI
不可达。两者作为**测试覆盖的引擎 API** 保留——MC 确定性、全随机 `1/P`、
预算/SE 停止规则均由 28 项测试覆盖——以备未来场景（半填手牌、更大预算）零改码启用。

**为何停用**：蒙特卡洛要逼近精确枚举直接给出的精度，需要极大的迭代量——
**计算成本太高，而结果本身仍带不确定性**（统计抽样误差，任何固定的迭代次数都无法
消除）。页面又总是齐牌、精确枚举总在预算内且**零抽样误差**，因此 MC 主模式被停用，
仅保留 100ms 预览（外加测试覆盖）。**后续规划**：优化算法实现，将蒙特卡洛作为
主模式完整开启。

**预估胜率以什么为条件**：即使是带 `provisional` 标记的临时数字，也是以牌桌上的
实际状态为输入——已选的手牌与已发的公牌都是**固定**条件。每次预览迭代保持它们
不变，只从牌堆抽样尚未发出的牌（页面上手牌必然已知，因此就是尚未翻开的公牌槽）。
所以预览回答的是与精确枚举完全相同的条件问题——“给定这些手牌和这副公牌，谁会赢？”
——区别只在于抽样一部分发牌结果而非枚举全部。它是同一个量的快速估计，不是另一个量。
